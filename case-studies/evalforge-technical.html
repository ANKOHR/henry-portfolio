EvalForge: how it works.

Seeded, versioned evaluation-set generation with lint, coverage checks, and diffs.

Problem

Evaluation data can drift

An evaluation set that changes without a reproducible record makes comparisons hard to interpret. Missing failure-mode coverage can leave a declared risk untested.

Constraints

Reproducibility and visible changes

The same specification and seed must produce identical bytes. Contents and coverage changes must be inspectable.

Design

Generate, lint, and diff

A task specification and seed drive generation. Lint and version diffs make the resulting evaluation data reviewable before it is used.

Implementation

Seeded, versioned eval sets

EvalForge generates seeded, versioned sets, checks coverage of declared failure modes, and compares versions. Its public repository is github.com/ANKOHR/evalforge-suite.

Failure modes

Catch invalid specs and coverage gaps

Lint and coverage checks make incomplete or malformed specifications visible. Changes to the specification or seed appear in the generated version and diff.

Testing

13 passing tests

The project has 13 passing tests. The same spec and seed produce byte-identical output.

Result

A published evaluation set tool

The repository is public and linked from the case study.

Commercial applicability

Build a repeatable regression gate

The AI evaluation service combines repeatable evaluation data with checks and a regression gate for an AI product.

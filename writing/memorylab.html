MemoryLab

MemoryLab is a deterministic benchmark harness that runs the same synthetic recall episodes through six memory policies and reports task success, token use, retrieval accuracy, and fabricated-recall (corruption) counts. No trained models, no embeddings: token overlap is literal word matching over fictional facts.

Problem

The problem

Memory designs for agents trade context size against retrieval quality and correctness. Keep everything and pay in tokens; summarize and risk losing facts; retrieve selectively and risk missing the right one. Comparing these designs requires running them on the same tasks, because a policy can look good on one episode and fail on another, and the failure may be in what it stored, what it retrieved, or what it fabricated.

The naive comparison is vibes: run each design once on a few examples and eyeball the answers. That confounds the policy with the episode and gives no way to count failure modes separately. A fair harness fixes the episodes, fixes the queries, fixes the token budget, and records per-query evidence: which facts were retrieved, how many tokens the context used, and whether the answer matches the planted truth.

A subtler trap is judging a compact context only by what it stores. A lossy summary that uses 30 tokens looks efficient until you count the fabricated recalls it causes. MemoryLab reports task success, token use, retrieval accuracy, and corruption side by side, so compactness and correctness are visible together instead of one hiding the other.

Design

Design

The flow is fixture episodes, then the runner, then per-query answers with evidence IDs and token counts, then metrics, then deterministic JSON run output or a findings report. fixtures.py writes the canonical episodes.json with seed 0 and no RNG, so the task set is fixed before any policy runs.

runner.py streams episodes: facts arrive through observe(), and queries pause the episode and call respond(query, token_budget). policies.py implements six policies behind one interface with observe, respond, and inspect: full_context (all events, newest first), summary (one lossy note per relation), token_overlap (literal shared-word ranking, not embeddings), episodic (time-tagged store), structured (typed key/value with set, correct, and expire operations), and hybrid (typed state plus timeline plus overlap fallback). The shared interface is what makes the comparison fair: every policy sees the same stream and answers under the same budget.

metrics.py computes task success rate, token counts, retrieval accuracy, and corruption counts. Each answer carries evidence IDs, so a correct answer can be traced to the facts that supported it. report.py emits Markdown or HTML findings. The protocol is fixed and declared up front: 4 episodes, 6 policies, 7 queries, and a per-query memory budget of 128 tokens in the findings.

Engineering decisions

Engineering decisions

Token accounting is deliberately simple and hand-checkable: tokens are whitespace-separated, so a count can be verified by eye. The memory token budget applies per query, not per episode; the query text counts toward total tokens but sits outside the memory budget, which keeps the budget about what the policy chose to retain rather than about the question asked.

The benchmark includes a deliberate corruption trap: the summary policy attaches Noah's value to Mira, which makes lossy behavior visible as a concrete fabricated recall rather than an abstract quality drop. Correct abstentions count as successes, never as corruptions, so a policy that says it does not know is rewarded for honesty instead of being punished for silence.

Retrieval is fully deterministic. Token overlap counts unique shared words with defined tie-breaks, and the structured policy's set, correct, and expire rules are explicit state transitions. No random generator and no model call appear anywhere in the fixture suite, so every policy's run is byte-deterministic and any rerun reproduces the same numbers.

Reports are required to contain protocol, results, findings, limits, and honesty sections. That structure forces the write-up to state what the numbers do and do not show, including the explicit limit that the findings apply to these fixtures only and do not establish which architecture is best in general.

What the tests verify

What the tests verify

The suite has 24 tests across four files: test_policies (9), test_report_cli (7), test_runner_metrics (5), and test_fixtures (3). They verify byte-identical fixture generation and synthetic labelling; per-policy semantics (summary keeps one latest note per relation and exposes the collision, token overlap counts unique shared words with defined tie-breaks, structured set/correct/expire rules, and the memory budget capping context); hand-computed metric verification; byte-deterministic runs for every policy; and report structure.

The hand-computed metric checks are the load-bearing ones: success rates, retrieval accuracy, and corruption counts are worked out independently in the tests, so the suite verifies the arithmetic behind the findings, not just that the code executes. Report tests assert the required sections exist, which keeps the honesty boundary from silently disappearing.

Scope and evidence

Scope

What it is not: there are no trained models, no embeddings, no real agent memory, and no retrieval systems here. Token overlap is literal word matching, the characters and facts are fictional, and the findings apply to these fixtures only. The report states they do not establish which architecture is best in general.

What the evidence supports: on 4 episodes and 7 queries at a per-query budget of 128 tokens, full_context, token_overlap, episodic, structured, and hybrid all reached 100 percent task success and 100 percent retrieval accuracy with 0 corruptions, while summary reached 71.43 percent (5 of 7) with 50 percent retrieval accuracy and 2 corruptions. Memory-token totals were summary 30 of 896, hybrid 39, structured 54, and the others 107. Those numbers describe the fixture suite, and only the fixture suite. The 24 tests verify the harness mechanics that produced them.

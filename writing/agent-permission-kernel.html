Agent Permission Kernel

The Agent Permission Kernel compiles YAML capability policies into per-agent grants, checks each synthetic operation before it runs, enforces directory boundaries and spend caps with idempotent charges, and records every allow, deny, or escalation in an ordered audit trail.

Problem

The problem

Broad permission strings like "can use email" hide which operations are actually allowed, and a filesystem grant can silently cover more paths than intended. When an agent acts, the decision about what it may do is usually buried inside the agent or the tool code, which makes it hard to review, test, or audit independently of the agent's behavior.

The kernel approach separates the permission question from execution. A policy file declares what each agent may do using explicit capability tokens. A compiler validates the policy and turns it into typed grants; a separate kernel matches each proposed operation against those grants and returns allow, deny, or escalate before any adapter executes anything.

This matters because the failure mode of permission systems is silent over-granting: an operation that should have been denied succeeds because the check was approximate, because two tokens composed in a way that was never intended, or because the policy was stale. The kernel makes each of those decisions explicit, named, and recorded.

Design

Design

The pipeline has four stages. compiler.py validates a YAML policy: token types must be known, filesystem scopes must be canonical absolute paths, and conflicting duplicate or spend-cap grants are rejected with named errors. The compiler emits compiled per-agent grants, with the data models held in model.py.

kernel.py matches each proposed fixture operation against those grants and returns one of three verdicts: allow, deny, or escalate. Denials and escalations carry one of 8 named reason codes, so a refusal is never a bare boolean: it explains itself. Spend is accounted with decimal arithmetic, and charges are keyed by transaction ID, so repeating the same agent, transaction ID, and amount is idempotent and never double-charges.

Adapters in adapters.py provide the synthetic executors: fake Gmail, an in-memory fake filesystem dictionary, a fake spend ledger, and a fake production deploy. runtime.py runs named scenarios (privilege_escalation, spend_overflow, full_demo), reporting.py generates Markdown and HTML reports with audit output, and cli.py exposes five commands: apk check, apk simulate, apk escalations decide, apk report, apk audit. State (audit trail, spend ledger, escalation queue) persists as JSON under .apk/, overridable with --state-dir.

Audit entries carry a fixed fixture timestamp (2026-09-29T00:00:00Z) and entry order is event order, so repeated identical decisions serialize identically through normalized serialization.

Engineering decisions

Engineering decisions

Directory-boundary scope matching is exact, not prefix-based: /data covers /data/file but not /database, and /, relative paths, and traversal components are rejected as over-broad. This closes the classic path-confusion gap where a grant for /data silently included /database.

Capability tokens are non-composable by default: gmail.draft never implies gmail.send, so drafting permission cannot be parlayed into sending permission. The default fixture_writer policy shows the intended posture: gmail.read and gmail.draft, /data read, /tmp write, a $5 spend cap, and prod.ask, with no send and no /data writes.

Escalations are single-decision and stable: prod.ask queues a human decision with a stable ID, a recorded decision can never be overwritten, and a retried deploy returns the stored human decision plus an agent notification. The human-in-the-loop step becomes replayable and auditable rather than a one-off side channel.

The spend_overflow scenario demonstrates the cap mechanics concretely: a $3 charge then a $2 charge are allowed, the next $1 charge is denied, and the ledger sits at exactly $5. The only runtime dependency is PyYAML (Python 3.10+); everything else is stdlib, which keeps the trusted computing base small.

What the tests verify

What the tests verify

28 test functions across 5 files: test_kernel (9) covers kernel decisions against compiled grants; test_compiler (5) covers policy validation errors; test_adapters (3) covers synthetic adapter behavior; test_simulation_reporting (4) covers scenario runs and report generation; test_cli (7) covers the CLI flows end to end.

Key scenarios verified include draft allowed versus send denied, directory boundary matching (/data/file allowed, /database denied), exact-cap and over-cap spend behavior, deterministic decisions, duplicate charge idempotency, the production escalation flow, human approvals and denials, and audit entry ordering. Simulation and CLI checks confirm the report includes the synthetic-data notice.

Scope and evidence

Scope

All operations are synthetic fixtures. This is not an operating-system sandbox, not real Gmail, and not a production security boundary: the filesystem adapter never reads or writes host files, and a green decision only authorizes the corresponding synthetic adapter action. The reports repeat this boundary explicitly.

What the repository does verify, with evidence, is the mechanics of a capability system on synthetic ground: policy compilation with named validation errors, boundary-exact scope matching, idempotent decimal spend accounting, single-decision escalations, and a deterministic ordered audit trail, all covered by 28 test functions. It is a design exercise with real engineering decisions, not a deployable access-control product.

Repo Surgeon

Repo Surgeon applies deterministic Python AST heuristics to a repository: it builds a local import graph with cycle paths, flags likely dead code and measured code smells, highlights test gaps by name matching, and assembles the findings into an evidence-linked staged remediation plan.

Problem

The problem

A repository review usually starts with questions that are expensive to answer by hand: how do modules connect, is there an import cycle, where does suspicious complexity concentrate, and which modules lack tests? Answering from reading alone is slow, and the answers go stale as soon as the code changes.

Repo Surgeon turns those questions into review candidates that point back to source locations. It parses the repository with the AST, builds the local import graph, applies dead-code heuristics, measures code smells against named thresholds, matches modules and public functions against test files, and orders the results into a staged plan. Every finding carries file and line evidence.

The critical design choice is framing: findings are review candidates, not verdicts. Static analysis can show that a symbol has no static path from any entry point, but it cannot know whether a framework, plugin, reflection, or generated code uses it. The tool reports evidence and lets the human decide.

Design

Design

scan.py parses the repository with the AST, sorting repo-relative paths first and emitting sorted records, which is the foundation of the determinism guarantee. analysis.py derives the local module and import graph with cycle paths, applies dead-code heuristics (modules with no static path from main.py, cli.py, __main__.py, or test files, plus unreferenced public functions), computes smell measurements, and matches module and public-function names against test files and test functions to find gaps. Syntax errors are listed as parse errors and unparsable files are excluded rather than silently dropped.

report.py groups candidates into three tiers: safe review candidates, review-needed refactors, and architectural work, and emits JSON, Markdown, or HTML. The HTML report carries a visible static-heuristics banner. fixtures.py deterministically generates two labelled synthetic repositories for testing. The CLI (rsg) exposes seven commands: fixtures, graph, dead, smells, gaps, plan, report.

All analysis is read-only: it never edits source. There is no randomness, so the same input tree and Python version produce byte-identical JSON. Identifiers and literals are normalized before token comparison for duplication detection.

The planner orders candidate actions into a staged remediation list with finding order and effort estimates, so the output is a sequenced plan a reviewer can work through rather than a flat list of complaints.

Engineering decisions

Engineering decisions

The 5 smell detectors use inclusive, named thresholds rather than vibes: god module means more than 200 physical lines; near-duplicate functions require at least 12 normalized tokens and similarity of at least 0.85 (identifiers and literals are normalized before comparison); risky call means a direct eval, exec, or a call ending in .system; more than 5 parameters; nesting deeper than 4 blocks. Named thresholds make each finding checkable and debatable.

Byte-identical output is enforced through sorted paths and sorted records at every stage, which makes the tool's own output diffable across runs and versions. That is what makes it usable in a pipeline rather than just an interactive session.

Test gaps are found by name matching (module and public-function names against test files and test functions), not by runtime coverage measurement. This is a deliberate trade-off: it needs no instrumentation and no test run, at the cost of missing dynamically covered code and flagging code that is covered under a different name. The reports say this plainly.

The planted_issues fixture exercises every detector: an alpha.py and beta.py import cycle, dead_module.py with no static path from any entry point and no test, an over-threshold god_module.py, near-identical functions in duplicate_one.py and duplicate_two.py, an eval call in risky.py, and orphan_a.py (one of two test-less modules). The clean fixture is a small main.py with a test and no planted issues.

What the tests verify

What the tests verify

18 test functions across 7 files: test_cli (3), test_dead (2), test_determinism_report (2), test_fixtures (2), test_gaps_plan (3), test_graph (3), test_smells (3). They cover dead-code detection, graph and cycle detection, smell detectors, fixture generation, gaps and planning, and output determinism.

Assertions check graph paths, clean behavior on the control fixture, named evidence on findings, finding order and effort in the plan, fixture determinism, output stability (byte-identical JSON), and the visible static-heuristics notice in the HTML report.

Scope and evidence

Scope

Findings are static-analysis heuristics, not understanding of intent. Dead-code detection misses dynamic imports and runtime registration; a reachable symbol can still be unused and vice versa. Smell thresholds are screening rules, not quality judgments, and test gaps use name matching rather than runtime coverage. Human review must account for the application's loading and execution model.

What is verified with evidence is the mechanics of deterministic static review assistance: import-graph construction with cycle paths, named-threshold smell detection, name-based gap finding, and staged plan assembly, all covered by 18 test functions over two labelled synthetic repositories. It produces review candidates with evidence, not automated refactoring.

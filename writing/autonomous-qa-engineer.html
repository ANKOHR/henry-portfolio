Autonomous QA Engineer

The Autonomous QA Engineer crawls a web application over HTTP, builds a site map of pages, links, and forms, derives a request test catalogue from that map, executes the requests, and writes bug reports where every finding ships with the exact request that reproduces it.

Problem

The problem

A URL list does not capture what a request test should check: form fields and their constraints, links and their statuses, page-declared required elements, and response timing. Hand-written request tests drift from the application as pages change, and the reproduction evidence for a failure is usually a screenshot or a prose description rather than the request itself.

AQE derives tests from the application's own structure. It crawls the app over HTTP, records links, forms, form fields, required elements, response statuses, and HTML snapshots into a site map, then generates a test catalogue from that map alone: link checks, form cases, required-element checks, and response-time checks. Because the catalogue is derived, it reflects what the app actually serves.

The reporting discipline is the point: reporting.py groups related failed assertions into bugs, and each bug includes the full reproduction block, the exact method, URL, headers, and body that produced it. A bug report you can replay is worth more than one you can only read.

Design

Design

The pipeline runs in five stages through the CLI: aqe fixtures --serve, explore, generate, run, report. fixtures.py serves two synthetic applications (buggy and clean) using the standard-library HTTP server. explorer.py performs a same-origin HTTP GET crawl up to a depth limit, recording links, forms, form fields, page-declared required elements, response statuses, and saved HTML snapshots into the site map.

generator.py derives the test catalogue from the site map alone: link checks, form cases (including invalid-input cases), required-element checks, and response-time checks with a slow threshold that defaults to 180 ms and is configurable. No hand-written test cases are needed to cover a new page; the map drives everything.

executor.py submits the cases with urllib, measures each request, and stores the exact method, URL, headers, and body in results.json plus a deterministic bugs.json. Durations are omitted from bugs.json so identical findings compare byte-for-byte across runs. http_client.py is the HTTP-only client used throughout. There is no randomness anywhere, and ordering is normalized at every serialization boundary.

reporting.py groups related failed assertions into bugs and writes Markdown and HTML reports with full reproduction blocks. The severity rubric is explicit: High for HTTP 500 or server errors, Medium for error-status links, invalid form input accepted, or missing required elements, and Low for pages over the response-time threshold.

Engineering decisions

Engineering decisions

HTTP-only by design. There is no browser driver, no JavaScript execution, no rendering, and no screenshots: page snapshots are saved HTML bytes. This deliberate narrowing of scope makes every finding reproducible from request data alone, and it keeps the runtime to the Python standard library.

Determinism is treated as a feature, not a nicety. bugs.json omits durations so identical findings serialize identically, ordering is normalized at every serialization boundary, and there is no randomness anywhere. Two runs against the same app produce byte-comparable findings, which means regressions in the tool itself are detectable by diffing.

The buggy fixture plants exactly 5 bugs that exercise every part of the pipeline: /missing-page returns 404 (link check), the /contact form accepts empty required fields and an over-maximum name (form validation), /api/lookup?q= returns 500 on empty input (server error), /slow waits 350 ms against the 180 ms threshold (timing check), and /missing-heading declares h1 required but omits it (required-element check). The clean fixture has zero planted bugs, so output is checked against known expectations without connecting to any live service.

The boundary is stated in the code and the reports: the tool can target a real staging URL, but it only validates HTTP responses and returned HTML bytes. It does not test JavaScript behavior, rendering, or visual appearance.

What the tests verify

What the tests verify

15 test functions across 5 files: test_executor_reporting (5), test_explorer (3), test_fixtures (3), test_cli (2), test_generator (2). They cover crawling (recording fixture pages, forms, and the broken link, depth limits, invalid base URLs), catalogue generation from required elements and edge inputs, deterministic generation, and execution against both fixtures.

The tests verify that the expected planted findings appear with concrete request evidence (exact method, URL, headers, body), that the clean fixture produces no findings, and that reports disclose the HTTP-only boundary. The executor and reporting tests confirm the byte-deterministic bugs.json behavior.

Scope and evidence

Scope

The fixture applications are synthetic with planted bugs. The "browser" is an HTTP client: it does not execute JavaScript, render pages, or take real screenshots (snapshots are saved HTML). This is not real browser automation, JavaScript testing, or visual regression testing, and no such claim is made in the repository or its reports.

What is verified with evidence is the request-level QA loop on synthetic ground: structure-derived test catalogues, reproducible bug reports with exact request evidence, deterministic byte-comparable findings, and a named severity rubric, all covered by 15 test functions. It is a demonstration of reproducible HTTP-level testing discipline, not a replacement for browser-based QA.

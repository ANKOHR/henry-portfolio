SOP to Agent Compiler

SOPC compiles procedures written in its documented Markdown grammar into a versioned plan IR that can be verified, graphed, contract-tested, and simulated.

Problem

The problem

A procedure document can describe a workflow without making its control flow mechanically checkable. Step references can point at steps that do not exist, decision conditions can be vague prose, and consequential actions such as payments can sit on paths where no approval step guards them. A human reader might notice these gaps; a script consuming the document cannot.

The naive fix is to ask a language model to read the procedure and run it. That trades one unverifiable artifact for another: the model's interpretation is invisible, non-repeatable, and can drift between runs. SOPC takes the opposite route. Instead of interpreting free-form prose, it compiles a restricted, documented Markdown grammar into a typed plan, and every later stage (verification, test generation, graphing, simulation) works from that compiled plan rather than from the prose.

Design

Design

The pipeline starts with SOPC Markdown source. The grammar parser (sopc/parser.py) converts it into typed Step and Plan objects, and diagnostics carry file, line, and rule identity so every error points at the exact source location. The model layer (sopc/model.py) serializes the plan as deterministic JSON against the versioned Plan IR schema 1.0.

From the Plan IR, four branches fan out. The static verifier (verify.py) applies seven named rules, SOPC101 to SOPC107, covering references, decision conditions, retry and checkpoint rules, reachability, and whether consequential actions are guarded on every path. The test generator (generate.py) emits a pytest contract module for the plan. The SVG renderer (graph.py) produces a deterministic state graph. The simulated executor (executor.py) walks the plan through state transitions while appending audit events.

The CLI (sopc/cli.py) exposes six commands: fixtures, compile, verify, generate-tests, run, and graph. Six synthetic fixtures ship in fixtures/ (also bundled under sopc/fixtures/): two clean plans, employee_onboarding.md with parallel device and profile setup and refund_approval.md with human approval before payment; two broken plans that each target specific rule violations; and two malformed documents that exercise parse errors.

Engineering decisions

Engineering decisions

There is no language model or ML anywhere in the pipeline; compilation is purely grammar-based. Free-form prose is rejected with a diagnostic, never interpreted. This is a deliberate trade: the tool understands less, but everything it does is repeatable.

Human checkpoints are fail-closed. When a run reaches a checkpoint and no decision was supplied (through --decisions or an interactive prompt), execution returns paused instead of guessing. Decision and condition expressions are never evaluated by an engine; their outcomes are passed explicitly through --decisions, --conditions, --outcomes, and --checks, so every input to a run is visible on the command line.

Retry backoff is a simulated delay recorded in the event log, never a real sleep, which keeps runs fast and deterministic. The CONSEQUENTIAL_ACTION_REQUIRES_HUMAN_CHECKPOINT rule uses dominator analysis: every path to a payment, external send, or deletion must pass through a human checkpoint. That is stronger than a local check on the action itself because it reasons about the whole graph. The tool is offline and local; no command contacts a public service.

What the tests verify

What the tests verify

The suite holds 27 test functions across 7 files. test_parser (5) checks grammar acceptance and rejection with exact file, line, and rule diagnostics. test_model (3) covers the schema. test_verify (4) exercises the named verifier rules. test_executor (8) covers checkpoints, paused runs, approvals, rejections, edits, retries, permission denial, and explicit condition results. test_graph (2) and test_cli (4) cover rendering and the command surface.

test_determinism (1) confirms stable ordering and byte-identical output across repeated runs, with no RNG anywhere in the codebase. Separate checks compare generated graphs and compilation output run over run, so determinism is tested as a property, not assumed.

Scope and evidence

Scope

SOPC does not understand arbitrary natural language. Only documents written in the supported SOPC Markdown grammar compile; anything else is rejected at parse time. All six fixtures are explicitly synthetic and fictional, and the executor runs plans against deterministic simulated adapters, never real tools.

What exists as evidence is the checked-in design itself: the parser with exact diagnostics, the seven named verifier rules, the generated pytest contract tests, the deterministic SVG renderer, and the 27-function test suite. The generated contract tests verify the plan contract and simulator behavior; they make no claim about production behavior.

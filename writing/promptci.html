PromptCI

PromptCI treats prompt changes like code changes: it detects prompt edits against a release record, runs only the linked eval suites, diffs deterministic per-case score, cost, and latency against a stored baseline, and applies named release gate rules before anything ships. Fixture providers are local Python scripts, not model calls.

Problem

The problem

Changing a prompt can alter output quality, cost, and latency at the same time, and teams often ship prompt edits with no more ceremony than a commit message. Without a baseline, a small wording tweak that silently drops expected tokens or doubles per-request cost is invisible until someone reads the bill or a user complains. Prompts are code that runs on every request, but they rarely get the release discipline that code gets.

The naive fix is re-running the whole eval suite on every change. That is slow, and it answers the wrong question: what you need to know is what changed relative to the last accepted release, and whether that change crosses a rule you wrote down in advance. Running everything also wastes the one signal that matters, which is the diff.

A second failure mode is letting a failed candidate become the new baseline. If every run overwrites the reference numbers, regressions ratchet: each release is compared against a slightly worse past, and the gate never fires. The accepted baseline must be protected from candidates that did not pass.

Design

Design

engine.py is the core. It hashes prompt files plus versions against the last accepted release; no change produces a named SKIPPED noop. Changed prompts map to affected suites only, scripted fixture providers run, and per-case score, cost, and latency are diffed against the baseline before gate rules apply in a fixed order.

Project files are human-readable JSON: promptci.json, prompts.json, providers.json, and suites.json. Run state lives in .promptci/ as latest-run.json, latest-diff.json, latest-gate.json, release.json, and baseline.json. A passing gate writes a new release record and replaces the baseline; a failing gate never touches the accepted baseline, which closes the ratchet problem at the storage layer rather than by convention.

Scoring is explicit and hand-checkable. Per-case score is expected-token recall: case-insensitive, duplicate tokens count, and an empty expected scores 1 only when the output is also empty. Case cost is (input plus output tokens) times provider cost per token. Latency is base milliseconds plus per-token milliseconds times total tokens. The tokenizer is whitespace, with no RNG or seed anywhere in the pipeline.

Gate rules are checked in a fixed order: regression count, then cost increase, then latency increase, then pass. The first exceeded rule is the named reason for a blocked release, so a failure message says exactly which budget broke. Defaults are 0 allowed regressions, 10 percent cost, and 20 percent latency, with thresholds inclusive at the limit. A blocked gate exits with status 1, so it composes with shell CI.

Engineering decisions

Engineering decisions

Change detection is hash-based, so evaluation only runs when a prompt actually changed, and the SKIPPED record still explains the no-change state. This keeps the pipeline honest about what it did and did not check: a quiet run is a recorded decision, not an absence of evidence.

Fixture providers are short deterministic Python scripts with declared price and latency profiles: summary_fixture at $0.000002 per token with 40 ms plus 2 ms per token, and classifier_fixture at $0.000001 per token with 25 ms plus 1 ms per token. They make no provider request, which makes the release calculation repeatable and lets tests hand-check the comparison formulas without credentials or network access.

The fixtures plant two distinct failure modes across three scenarios (baseline, regression, cost). The [fixture:summary:omit-detail] marker plants a regression by dropping expected words, which the score diff catches. The [fixture:classify:verbose] marker raises tokens, cost, and latency without changing score, which the budget gates catch. This separates "worse answers" from "same answers, more expensive" as independent gate reasons, and each scenario exercises a different rule.

The accepted baseline is protected by construction: only a passing gate writes a new release record and replaces the baseline. A failing gate keeps the old release and names the regression reason, so the reference numbers always describe the last thing that was good enough to ship.

What the tests verify

What the tests verify

The suite has 14 tests in a single file. They cover byte-deterministic fixture generation; the change trigger and affected-suite selection; planted regression attribution with before and after scores; hand-computed cost and latency deltas matched against the declared fixture profiles; the failing gate keeping the release and naming the regression reason; the passing gate writing a release plus a new baseline; cost and latency budget gates blocking with named reasons; report contents; and CLI flows including the failure exit status.

The hand-computed deltas are the load-bearing checks: the tests do the cost and latency arithmetic independently from the declared provider profiles and compare the engine's numbers against them. Attribution tests check that the planted regression is blamed on the right change with the right before and after scores, not merely that some gate failed.

Scope and evidence

Scope

What it is not: fixture providers are deterministic scripts, not model adapters. There are no real model calls, no live provider data, no real costs, no credentials, and no network access. The README calls it "a prompt change management demonstration, not a production readiness claim", and the boundary is repeated in every CLI command and report.

What the evidence supports: the mechanics of prompt-change CI on synthetic cases: hash-based change detection, affected-suite selection, per-case diffing against a protected baseline, and ordered gate rules with named failure reasons. The 14 tests verify those mechanics end to end, including the guarantee that a failed candidate never becomes the new baseline.

BrowserBench Local

BrowserBench Local grades browser agents on pages that fight back: prompt injections, conflicting data, and ambiguous instructions, all on local fixture pages that never touch the live web. A DOM-backed simulator executes scripted agents, 17 named scoring rules award additive partial credit, and reports carry per-criterion evidence. Standard library only; no browser is opened.

Problem

The problem

Browser tasks combine navigation, data entry, filtering, uploads, and judgment calls about conflicting or untrusted page content. Grading them by hand does not scale, and grading them on the live web is flaky, slow, and unsafe: a benchmark that can trigger real sends or real uploads during evaluation is a liability, not a tool.

The naive simulator is a happy-path script: it checks whether the agent reached the confirmation page and calls it a pass. That misses the interesting failures. An agent that submits a form with the wrong email but lands on the right page is not mostly right; it failed a specific criterion, and the score should say which one. Partial credit has to be per-criterion and additive, not a single fuzzy number.

The adversarial dimension is the point. Pages in the wild contain injected instructions, conflicting facts across two pages, and ambiguous requests where the safe move is to ask or defer. A benchmark that only tests cooperative pages teaches agents nothing about the cases that cause real incidents, so the fixture site plants traps on purpose and grades how the agent handles them.

Design

Design

Task definitions live in data/tasks/*.json: 8 tasks, each with an id, a start page, a goal, hand-checkable success criteria, partial-credit weights that sum to 1.0, and expected traps. tasks.py validates the definitions with named errors, rejecting missing fields, unknown rules, and credit weights that do not total 1.0, so a malformed task fails loudly at load time instead of producing a nonsense score.

fixtures.py generates a byte-identical static HTML site, with every page labelled synthetic and no remote assets. simulator.py parses the fixture HTML and executes declared actions (fill, read, click, navigate, upload, compare, clarify) against DOM-backed page state. agents.py holds scripted fixture agents with fixed action plans; the documented seed is none, because there is no randomness. A CLI serve command binds loopback port 8000 so the fixture pages can be inspected by hand.

scoring.py applies 17 named rules (value_equals, form_submitted, filter_matches, trap_avoided, conflict_detected, clarification_asked, not_sent, and others) with additive partial credit. For example, form-submit awards 0.15 for the correct name plus 0.15 for the correct email even when the submission itself fails, so the score decomposes into what the agent actually got right instead of collapsing to pass or fail.

report.py emits Markdown or HTML evidence reports with per-criterion points, trap outcomes, final DOM state, and the ordered action history. Scores derive from final simulator state and action history, never from an agent-provided score, so an agent cannot grade its own homework.

Engineering decisions

Engineering decisions

The environment is deliberately static and synthetic. The benchmark represents browser state in its own DOM-backed simulator instead of controlling a browser or executing site JavaScript, which removes an entire class of flakiness and makes every run reproducible. Nothing in the loop renders a page or runs page scripts.

Reports contain no timestamps, random IDs, or external requests, so reruns are byte-identical. Every episode records its actions in order with the source page and the outcome, which makes a disputed score auditable: you can walk the action history and see exactly which rule fired on which state.

The three documented adversarial tasks each test a different failure mode. ignore-injection checks that the trap is neutralized in state and in the action history, not merely that the final page looks right. resolve-conflict checks that both conflicting sources are flagged rather than one being silently preferred. defer-ambiguous checks that the agent records low confidence (0.5 or lower) and defers sending, with the not_sent rule confirming the local send state stayed inactive.

All uploads, submissions, checkouts, and trap activations change local simulator state only. Adversarial send controls are fixture state, not real side effects, which is what makes it safe to grade hostile pages: the worst case in an episode is a wrong value in a local data structure.

What the tests verify

What the tests verify

The suite has 35 tests across six files: test_simulator (7), test_fixtures (7), test_cli (6), test_tasks (6), test_scoring (6), and test_report (3). They verify byte-identical fixture output and action histories; that every task start page parses; that all pages are labelled synthetic with no remote assets; that required planted elements and every declared trap are present; form validation rejecting missing or bad email; search, dashboard filter, upload confirmation, and cart-carrying checkout flows; fact comparison deriving conflicts from two page observations; a hand-worked form episode awarding exact partial credit; the injection task neutralizing the trap in state and history; the conflict task flagging both sources; the ambiguous task recording low confidence and deferring; and task validation rejecting bad definitions.

CLI tests cover serving the fixture site on loopback, and the hand-worked scoring episode checks the partial-credit arithmetic against independently computed points, so the suite verifies the scoring math rather than just the plumbing.

Scope and evidence

Scope

What it is not: tasks run on local fixtures, never the live web. The agents are scripted fixtures, not real browser automation; there is no JavaScript execution, no rendering, and no real browser anywhere in the loop. Fixtures are fictional and labelled synthetic. Its adversarial send controls are local fixture state only.

What the evidence supports: deterministic grading of scripted agents on hostile fixture pages, with per-criterion partial credit, auditable action histories, and byte-identical reports. The 35 tests verify the simulator, the scorer, the fixtures, and the CLI on those terms, including the three adversarial tasks and their expected safe outcomes.
